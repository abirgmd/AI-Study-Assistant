Le cycle de vie d'un logiciel comprend l'expression des besoins, la conception, le développement, les tests, le déploiement et la maintenance. Chaque modèle de processus, en cascade ou itératif, organise différemment l'enchaînement de ces phases.
Le modèle en cascade enchaîne les phases de manière séquentielle : on ne commence la conception qu'une fois les spécifications validées. Simple à piloter, il supporte mal les changements de besoins découverts tardivement par le client.
La méthode Scrum organise le travail en sprints de deux à quatre semaines. Le Product Owner priorise le backlog, l'équipe s'engage sur un incrément livrable et le Scrum Master facilite les cérémonies comme la mêlée quotidienne et la rétrospective.
Une user story décrit un besoin du point de vue de l'utilisateur : en tant que client, je veux suivre ma commande afin de savoir quand elle arrivera. Elle s'accompagne de critères d'acceptation vérifiables par des tests.
Le diagramme de classes UML représente les classes d'un système, leurs attributs, leurs méthodes et les relations d'association, d'héritage et de composition. Il sert de support à la conception orientée objet avant l'écriture du code.
Le diagramme de séquence montre les messages échangés entre objets au cours du temps pour réaliser un cas d'utilisation. Il aide à vérifier la répartition des responsabilités entre les classes avant l'implémentation.
Le principe de responsabilité unique, premier des principes SOLID, stipule qu'une classe ne doit avoir qu'une seule raison de changer. Une classe qui gère à la fois la validation, le stockage et l'affichage devient fragile et difficile à tester.
Le principe ouvert-fermé recommande qu'un module soit ouvert à l'extension mais fermé à la modification. On ajoute un nouveau comportement en créant une nouvelle classe qui implémente une interface, sans retoucher le code existant déjà testé.
Le principe d'inversion des dépendances demande que les modules de haut niveau dépendent d'abstractions et non d'implémentations concrètes. L'injection de dépendances permet ensuite de remplacer une base de données réelle par un double de test.
Le principe DRY, Don't Repeat Yourself, invite à éviter la duplication de logique. Lorsque la même règle est codée à trois endroits, une correction oubliée à l'un d'eux suffit à créer une incohérence et un bug.
Un code smell est un symptôme dans le code qui suggère un problème de conception : méthode trop longue, classe fourre-tout, nombres magiques, paramètres trop nombreux ou duplication. Il ne s'agit pas d'un bug mais d'un signal pour refactoriser.
Le refactoring améliore la structure interne du code sans modifier son comportement observable. On procède par petites transformations, comme extraire une méthode ou renommer une variable, en relançant les tests après chaque étape.
Le patron de conception Stratégie encapsule une famille d'algorithmes interchangeables derrière une interface commune. Le client choisit l'algorithme à l'exécution, par exemple différents modes de calcul de frais de livraison.
Le patron Observateur permet à des objets de s'abonner aux changements d'état d'un sujet. Lorsque le sujet évolue, tous les observateurs sont notifiés automatiquement, ce qui découple l'émetteur des récepteurs.
Le patron Fabrique centralise la création d'objets. Le code client demande un objet par son type logique sans connaître la classe concrète instanciée, ce qui facilite l'ajout de nouvelles variantes.
Le patron Singleton garantit qu'une classe n'a qu'une seule instance accessible globalement. Souvent critiqué, il introduit un état global qui complique les tests unitaires et masque les dépendances réelles du code.
Un test unitaire vérifie une petite unité de code isolée, généralement une fonction ou une méthode. Il s'exécute en quelques millisecondes et suit la structure Arrange, Act, Assert pour rester lisible.
Les tests d'intégration vérifient que plusieurs composants fonctionnent correctement ensemble, par exemple un service métier et son dépôt de données. Ils détectent les erreurs d'interface que les tests unitaires isolés ne voient pas.
Les tests de bout en bout simulent le parcours complet d'un utilisateur à travers l'application. Plus lents et plus fragiles, ils sont moins nombreux que les tests unitaires selon la pyramide des tests.
Le développement piloté par les tests, ou TDD, impose d'écrire d'abord un test qui échoue, puis le code minimal pour le faire passer, et enfin de refactoriser. Ce cycle rouge, vert, refactor guide la conception par l'usage.
La couverture de code mesure la proportion de lignes ou de branches exécutées par les tests. Une couverture élevée ne garantit pas l'absence de bugs, car un test peut exécuter une ligne sans vérifier son résultat.
Un mock remplace une dépendance réelle par un objet simulé dont on contrôle les réponses. Il permet de tester un service sans appeler une API externe lente ou payante, et de vérifier les interactions attendues.
L'intégration continue consiste à fusionner fréquemment le travail des développeurs dans la branche principale. Chaque push déclenche automatiquement la compilation, les tests et l'analyse statique, ce qui détecte les régressions au plus tôt.
Le déploiement continu va plus loin que la livraison continue : toute modification qui passe le pipeline est mise en production automatiquement. Il exige une couverture de tests solide et des mécanismes de retour arrière rapides.
Git est un système de gestion de versions décentralisé. Chaque commit enregistre un instantané du projet ; les branches permettent de développer une fonctionnalité isolément avant de la fusionner par une pull request relue.
Une revue de code consiste à faire relire ses modifications par un pair avant la fusion. Elle détecte des erreurs, partage la connaissance du code et maintient des conventions communes au sein de l'équipe.
La dette technique désigne le coût futur des raccourcis pris aujourd'hui : code dupliqué, absence de tests, conception bâclée. Comme une dette financière, elle génère des intérêts sous forme de bugs et de lenteur de développement.
L'analyse statique examine le code source sans l'exécuter pour repérer des erreurs potentielles, des vulnérabilités ou des violations de style. Des outils comme SonarQube calculent aussi la complexité cyclomatique et la duplication.
La complexité cyclomatique compte le nombre de chemins indépendants dans une fonction. Au-delà d'une dizaine, la fonction devient difficile à comprendre et à tester exhaustivement ; il faut alors la découper.
La spécification des exigences distingue les exigences fonctionnelles, qui décrivent ce que fait le système, et les exigences non fonctionnelles, comme la performance, la sécurité ou la disponibilité attendues.
Le diagramme de cas d'utilisation identifie les acteurs du système et les services qu'ils en attendent. Il structure le recueil des besoins et sert de base au découpage en fonctionnalités et aux tests d'acceptation.
L'architecture en couches sépare la présentation, la logique métier et l'accès aux données. Chaque couche ne dépend que de la couche inférieure, ce qui permet de modifier l'interface sans toucher aux règles métier.
L'architecture hexagonale place le domaine métier au centre et l'entoure de ports et d'adaptateurs. Les bases de données, interfaces web et services externes deviennent des détails interchangeables.
Les microservices découpent une application en petits services autonomes déployés indépendamment. Cette approche facilite la mise à l'échelle d'une équipe mais ajoute la complexité des communications réseau et de la cohérence des données.
Le versionnage sémantique attribue des numéros de version de la forme majeur, mineur, correctif. Une version majeure signale une rupture de compatibilité, une mineure une nouvelle fonctionnalité compatible et un correctif une réparation.
Un bug suit un cycle de vie : signalement, qualification, reproduction, correction, vérification puis clôture. Un bon rapport de bug précise l'environnement, les étapes pour le reproduire, le comportement attendu et le comportement observé.
Les tests de régression rejouent les scénarios existants après chaque modification pour s'assurer qu'aucune fonctionnalité qui marchait auparavant n'a été cassée. Ils sont la principale justification de l'automatisation des tests.
Le mutation testing introduit volontairement de petites erreurs dans le code, comme remplacer un signe plus par un signe moins. Si aucun test n'échoue, la suite de tests est trop faible malgré une couverture apparente élevée.
La documentation technique d'un projet comprend un README, des commentaires de code utiles, des docstrings et une documentation d'architecture. Elle doit rester fidèle au code, sinon elle induit les développeurs en erreur.
Le pair programming réunit deux développeurs sur un même poste : l'un écrit le code, l'autre relit et anticipe les problèmes. Les rôles alternent régulièrement, ce qui améliore la qualité et la diffusion des connaissances.
Exercice : identifiez les code smells de la classe CommandeManager fournie, classez-les par priorité, puis proposez un refactoring en trois étapes en vérifiant à chaque étape que les tests existants passent toujours.
La gestion de configuration logicielle recense tous les éléments d'un projet, code, scripts, dépendances et paramètres, afin de pouvoir reconstruire exactement n'importe quelle version livrée.
Le Kanban visualise le flux de travail sur un tableau à colonnes, à faire, en cours, terminé. La limitation du travail en cours évite de multiplier les tâches commencées et met en évidence les goulots d'étranglement.
Le principe de substitution de Liskov exige qu'un objet d'une sous-classe puisse remplacer un objet de la classe mère sans altérer le comportement attendu. Un carré qui hérite d'un rectangle viole souvent ce principe.
Le principe de ségrégation des interfaces recommande plusieurs interfaces spécifiques plutôt qu'une interface générale. Un client ne doit pas être obligé de dépendre de méthodes qu'il n'utilise jamais.
Le nommage est une part essentielle de la lisibilité. Une variable nommée delaiLivraisonJours explique son rôle, alors que d ou tmp oblige le lecteur à reconstituer l'intention en lisant tout le code autour.
Les assistants de code comme GitHub Copilot génèrent des fonctions à partir d'un commentaire ou d'une signature. Le développeur reste responsable du code fusionné : il doit le relire, le tester et vérifier les cas limites oubliés.
Le BDD, développement piloté par le comportement, décrit les scénarios en langage naturel avec la syntaxe Étant donné, Quand, Alors. Ces scénarios lisibles par le client deviennent directement des tests automatisés.
La maintenance logicielle se décline en maintenance corrective, qui répare les défauts, adaptative, qui suit l'évolution de l'environnement, et évolutive, qui ajoute des fonctionnalités. Elle représente la majorité du coût d'un logiciel.
Un gestionnaire de dépendances comme Maven, npm ou pip déclare les bibliothèques utilisées et leurs versions. Épingler les versions garantit des constructions reproductibles et évite qu'une mise à jour casse le projet.
La programmation défensive vérifie systématiquement les préconditions des fonctions et traite explicitement les cas d'erreur. Une exception métier dédiée explique mieux le problème qu'une erreur générique levée loin de sa cause.
L'estimation des tâches en points d'effort compare la difficulté relative des user stories. Le planning poker fait voter l'équipe simultanément pour éviter que l'avis du plus expérimenté n'influence les autres.
Le diagramme d'états-transitions décrit les états successifs d'un objet, comme une commande créée, payée, expédiée puis livrée, et les événements qui déclenchent chaque transition. Il aide à repérer les transitions interdites.
Une API bien conçue est cohérente, prévisible et documentée. Le contrat d'interface doit être stable : modifier la signature d'une méthode publique impose de mettre à jour tous les appelants et souvent de changer de version majeure.
La qualité logicielle selon la norme ISO 25010 regroupe des caractéristiques comme la fiabilité, la maintenabilité, la portabilité, l'utilisabilité et la sécurité. Chaque caractéristique se décline en métriques mesurables.
Les tests de performance mesurent le temps de réponse et le débit d'une application sous charge. Ils révèlent des goulots d'étranglement, comme une requête répétée dans une boucle, avant que les utilisateurs ne les subissent.
Le linting applique automatiquement des règles de style et détecte des erreurs simples comme des variables inutilisées. Intégré à l'éditeur et au pipeline, il évite les débats de style pendant les revues de code.
Le prototype jetable permet de valider rapidement une idée ou une interface avec le client avant d'investir dans une implémentation robuste. Il ne doit pas devenir le produit final, faute de quoi la dette technique explose.
La traçabilité relie chaque exigence aux éléments de conception, au code et aux tests qui la couvrent. Elle permet de mesurer l'impact d'un changement de besoin et de prouver que toutes les exigences sont vérifiées.
Le principe de moindre surprise demande qu'une fonction fasse ce que son nom annonce, sans effet de bord caché. Une méthode getTotal qui modifie aussi le panier surprendra le prochain développeur et provoquera des bugs difficiles à diagnostiquer.
